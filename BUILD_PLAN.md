## Step 2 — Loaders

**Architecture point:** *"get text out of whatever this is"*, and normalise early so nothing
downstream knows the file format. This is also where **document authority** is stamped
(DESIGN.md §b.4).

```
Implement rag/loaders.py per DESIGN.md §b.4.

A `Loader` protocol with `matches(path) -> bool` and `load(path) -> list[RawDoc]`, and four
implementations, all returning the same RawDoc shape:

1. PdfLoader (pypdf) — one RawDoc per page so page numbers survive as citation anchors.
   Normalise whitespace INCLUDING non-breaking spaces (U+00A0 -> " "): the rendered tables use
   them, and without this BM25 cannot tokenise figures like "6,40,000" (DESIGN.md §b.4). Rejoin
   words broken across a line by a hyphen.
2. FaqLoader — matches faq.txt specifically. One RawDoc for the file; the chunker handles the
   Q&A splitting.
3. TextLoader — plain policy text (refund_terms.txt, eligibility_criteria.txt). One RawDoc.
4. YamlLoader — walk the tree and RENDER TO PROSE, do not dump YAML as a string. One RawDoc per
   top-level program record and per config block. Follow the §b.4 example: "Program SEF-101,
   Software Engineering Foundations. Duration 9 months. ... List tuition INR 210000 exclusive of
   GST." Numbers must appear verbatim so BM25 can still match "210000". Keep the original YAML
   fragment in RawDoc.extra.

Authority and defers_to, exactly per DESIGN.md §c.6 "Document-level defaults":
- A document whose header says "AUTHORITATIVE" or "single source of truth" is `authoritative`
  (refund_terms.txt, placement_policy.pdf, program_pricing.yaml). eligibility_criteria.txt has
  no such line but is the sole source for its content: `authoritative`.
- course_brochure.pdf is `reference`, with document-level defers_to = the pricing, eligibility
  and placement document IDs, taken from its own "Next steps" section.
- faq.txt is `reference` at document level; individual FAQ chunks become `summary` in the
  chunker when they carry a defers_to (see Step 3).
- Extract every document ID matching MA-[A-Z]+-\d{4}-\d{2} from a document's header for doc_id,
  and from its body for the document-level defers_to (excluding its own ID).
Also extract doc_title from the header. Put the heuristics in one small documented function,
not scattered through the loaders. "Overlapping topic" is never judged by code — the explicit
defers_to IDs are the only signal, by design.

Expose `load_corpus(corpus_dir) -> list[RawDoc]`, dispatching by matches(), sorted by filename
for determinism. Raise a clear error if the corpus dir is empty or missing.

Commit as "feat(ingest): per-type loaders with authority detection".
```

**Verify:** a throwaway script printing `(source_file, doc_id, authority, page, len(text))` for
every `RawDoc` — expect 6 files, PDFs expanded to one doc per page.

## Step 3 — Chunker

**Architecture point:** the highest-leverage component. Structure-first splitting plus the
breadcrumb header (DESIGN.md §b.1–b.3).

```
Implement rag/chunker.py per DESIGN.md §b.

Algorithm exactly as §b.2 specifies:
  units = split_on_structure(doc)   # per doc_type
  oversized units -> paragraph-aligned sliding window (MAX_CHARS, OVERLAP_CHARS)
  runt units (< MIN_CHARS) -> merged forward into the next unit, EXCEPT faq Q&A pairs, which
                              are indexed as-is however short (§b.3: the question line is the
                              retrieval signal; merging two questions blurs it)
  every emitted chunk -> prefixed with a breadcrumb header

Structure splitters by doc_type, per the §b.4 table:
- faq  -> one chunk per Q&A pair. Split on the /^Q\d+\.\d+/ marker. NEVER split a question from
          its answer, even if the pair exceeds MAX_CHARS.
- text -> "===" banner sections first, then "---" dashed sub-banners (eligibility 3.1-3.5 use
          these), then numbered clauses (2.1, 5.3). Keep clause numbers IN the chunk body —
          agents cite "§5.3" so it must be retrievable. Strip banner rule characters from the
          body but keep the section title as metadata.
- pdf  -> headings detected BY SHAPE, not markup — the PDF text contains no "##" markers; those
          existed only in the script that generated it. A line is a heading if it is short
          (< 80 chars, no terminal full stop) and matches one of: a program code
          (^[A-Z]{3,4}-\d{3}\b), ^Module \d, a numbered clause (^\d+(\.\d+)?\s), or a known
          title word (Syllabus, Capstone projects, Career outcomes, Instructors, Certification).
          Keep the regexes in one list so a missed heading is a one-line fix, and print the
          headings found per page during ingest. Carry the last-seen heading forward across a
          page break so a section split over two pages keeps its title.
- yaml -> one chunk per rendered record; these are already chunk-sized.

Per-chunk defers_to and authority (DESIGN.md §c.6): extract every MA-[A-Z]+-\d{4}-\d{2} ID from
the chunk body (excluding the chunk's own doc_id), union the document-level list from RawDoc.
A faq chunk with a non-empty defers_to is stamped authority="summary"; other chunks inherit the
document's authority.

Breadcrumb header format, exactly as §b.2:
  [<doc_title> | <doc_id> | §<section>]   with " | page N" appended when page is not None
It is prepended to Chunk.text (the embedded/indexed text) and excluded from Chunk.body.

Set content_hash = sha256 of the body, used for idempotent ingestion.

Expose `chunk_documents(docs, settings) -> list[Chunk]` with stable, deterministic chunk_ids of
the form "<source_file>::<n>".

Then print a distribution summary (count, min/median/max char_len, per-document counts) so I can
check it against DESIGN.md §b.3's expected 140-180 chunks. If the count is far outside that
range, say so rather than quietly proceeding.

Commit as "feat(ingest): structure-aware chunker with breadcrumb headers".
```

**Verify:** chunk count in the 140–180 band; eyeball 5 random chunks — each should be
self-describing, with no Q severed from its A and no clause number lost.

## Step 4 — Embeddings

**Architecture point:** pluggable dense representation; primary + fallback + opt-in
(DESIGN.md §c.1).

```
Implement rag/embeddings.py per DESIGN.md §c.1.

An `Embedder` protocol: `embed_documents(texts) -> np.ndarray`, `embed_query(text) -> np.ndarray`,
plus `name` and `dim` properties. All vectors L2-normalised on the way out, so cosine is a dot
product (§c.3).

Three implementations:
1. FastEmbedEmbedder (PRIMARY) — fastembed with BAAI/bge-small-en-v1.5, 384 dims, ONNX on CPU.
   bge models want an instruction prefix on QUERIES only ("Represent this sentence for searching
   relevant passages: "), not on documents — implement that asymmetry and comment why.
2. LsaEmbedder (FALLBACK) — pure NumPy TF-IDF then truncated SVD. dim = min(128, n_chunks - 1)
   per §c.1. It is corpus-fitted, so it must expose fit(corpus_texts) and persist its learned
   state (vocabulary, idf, components) next to the index so embed_query works in a later process.
   No scikit-learn — numpy.linalg.svd is fine at this size.
3. OpenAIEmbedder (OPT-IN) — text-embedding-3-small, batched. Never auto-selected.

`get_embedder(settings)` resolves EMBEDDING_BACKEND:
  "auto" -> try fastembed, fall back to LSA on ImportError or model-download failure, and log
            clearly at WARNING which backend was chosen and why.
  explicit value -> use it, and fail loudly if unavailable rather than silently downgrading.

Commit as "feat(retrieval): pluggable embedder, fastembed primary with LSA fallback".
```

**Verify:** embed three sentences, two related and one unrelated; confirm the related pair scores
higher. Print which backend was selected.

## Step 5 — Store

**Architecture point:** SQLite + FTS5 + NumPy matrix. One file, no services (DESIGN.md §c.2).

```
Implement rag/store.py per DESIGN.md §c.2.

SQLite schema in index/rag.db:
- chunks(chunk_id PK, text, body, source_file, doc_title, doc_id, doc_type, section, page,
         authority, char_len, content_hash, vector_row INTEGER)
- chunks_fts — FTS5 virtual table over the chunk text, external-content against chunks, with
  triggers keeping it in sync. This is the BM25 arm.
- traces — the full §e schema; create it here so traces and chunks share one database and a
  failure investigation is a single SQL join.
- meta(key, value) — embedding backend name, dim, chunk count, built_at, corpus fingerprint.

Vectors: a single float32 .npy matrix at index/vectors.npy; chunks.vector_row is the row index.

A `Store` class with a narrow interface, exactly as §c.2 promises, so a swap to pgvector is one
file: add_chunks(chunks, vectors), dense_search(qvec, k) -> [(chunk_id, cosine)],
bm25_search(query, k) -> [(chunk_id, bm25_score)], get_chunks(ids), count(), meta get/set,
write_trace(row), plus reset().

dense_search: load the matrix once, cache it on the instance, and score with a single
`matrix @ qvec` — vectors are already normalised so that IS cosine.
bm25_search: use FTS5 bm25() and note in a comment that it returns NEGATIVE scores where lower is
better; negate so higher is better everywhere in this codebase. Sanitise the query into a safe
FTS5 MATCH expression (quote terms, drop operators) so user punctuation cannot throw.

Commit as "feat(store): SQLite + FTS5 + numpy vector store".
```

**Verify:** insert 3 fake chunks, run both search arms, confirm ids and score ordering.

## Step 7 — Retriever

**Architecture point:** hybrid dense + BM25, RRF fusion, authority re-ordering
(DESIGN.md §c.3–c.6). Deliberately built and testable **before** any LLM is involved.

```
Implement rag/retriever.py per DESIGN.md §c.3-c.6.

`Retriever.retrieve(query, expanded_query=None) -> list[RetrievedChunk]`:
1. Dense arm: embed_query(ORIGINAL query only) -> store.dense_search(CANDIDATES_PER_ARM).
2. Sparse arm: store.bm25_search(expanded_query or query, CANDIDATES_PER_ARM).
   Per §c.5 the expansion goes to the sparse arm ONLY, so a bad expansion cannot poison both arms.
3. Fuse with RRF: score = sum over arms of 1/(RRF_K + rank), RRF_K=60, rank 1-based.
4. Authority re-ordering, exactly the §c.6 pseudo-code:
     for chunk in fused: if chunk.defers_to and any(other.doc_id in chunk.defers_to for other
     in fused): chunk.rrf_score *= AUTHORITY_PENALTY   (0.8)
   A chunk is demoted ONLY when a document it explicitly points at is already in the result set.
   It must reorder, never filter — keep the penalty a named setting and comment the intent.
5. Miss detection per §c.4 — there is NO floor on the fused score (the doc explains why it cannot
   work). Compute from the RAW arm signals before fusion:
     dense_miss  = top cosine < MISS_DENSE_COSINE
     sparse_miss = FTS5 matched no query term outside the stopword list (English stopwords PLUS
                   the domain list in settings: meridian, academy, program, course, learner,
                   offer, support), or top BM25 < MISS_BM25_FLOOR
     hard_miss   = dense_miss and sparse_miss
   Return hard_miss alongside the results (a RetrievalResult with chunks, top_score, score_gap,
   hard_miss, and the raw arm signals) so the answerer and tracer can use it.
6. Truncate to TOP_K, populate every score/rank field on RetrievedChunk (both arms' scores AND
   ranks — DESIGN.md §e.2 depends on per-arm ranks to localise a failure).

Add `python main.py --search "..."` printing a ranked table: final_rank, doc, section, page,
authority, defers_to, dense_rank/score, bm25_rank/score, rrf_score, and a text preview, then a
footer line with top_score, score_gap, dense_miss, sparse_miss, hard_miss. No LLM involved —
this is the retrieval debugging tool §e.2 step 3 assumes exists.

Then run these four and show me the tables:
  "What is the refund policy?"                     (expect Refund Terms above the FAQ summary,
                                                    with Q6.1 visibly penalised)
  "Can I pay in monthly instalments?"              (expect pricing YAML / FAQ section 3)
  "minimum MAT score for DSML-301"                 (exact-token query, BM25 should dominate)
  "Does Meridian offer a cybersecurity program?"   (expect hard_miss=True — the abstention path)

Also in this step, while retrieval is fresh: write eval/test_cases.json (the 12 cases from
DESIGN.md §f.1, schema in Step 12) and the DETERMINISTIC half of eval/run_eval.py — Recall@k
only, runnable with --no-judge. It needs no LLM, and it means the eval exists before the clock
gets tight. Report recall@5 now.

Commit as "feat(retrieval): hybrid BM25 + dense retrieval with RRF and authority ordering".
```

## Step 8 — LLM client

**Architecture point:** provider-detecting, so it runs whichever key the grading machine has
(DESIGN.md §a.3 decision 8).

```
Implement rag/llm.py — a thin provider-agnostic client. No framework.

`LLMClient` with: complete(system, user, schema=None, max_tokens, effort="low") -> LLMResponse
(text, parsed dict when schema given, input_tokens, output_tokens, model, latency_ms).
No temperature parameter anywhere in the interface: current Anthropic models return a 400 for
temperature/top_p/top_k. Determinism for the judge comes from a fixed rubric, low effort, and a
strict output schema (DESIGN.md §f.2).

Provider resolution: LLM_PROVIDER, else auto-detect from the key read from SCALER_LLM_API_KEY —
a key starting "sk-ant-" is Anthropic, otherwise OpenAI. Log the resolved provider and model at
startup, never the key.

Anthropic path (the primary, documented path): the official `anthropic` SDK, model claude-opus-5,
adaptive thinking (the default — do not pass budget_tokens), output_config.effort from settings,
and structured output via output_config.format (or client.messages.parse) for the schema. Do not
use assistant prefill — it is rejected on current models. Do not pass temperature.
OpenAI path: the official `openai` SDK behind the same interface, model from env with a sensible
default, JSON-schema structured output.

Requirements for both: a hard request timeout, bounded retries with exponential backoff on
429/5xx/connection errors only (never on 400), and typed exceptions surfaced as one
`LLMError` carrying the stage. If the key is missing, raise a clear, actionable error naming
SCALER_LLM_API_KEY — the system must fail understandably, not mysteriously.

Add `python main.py --check-llm` that makes one trivial call and prints provider, model, latency,
tokens. Commit as "feat(llm): provider-detecting LLM client with structured output".
```
